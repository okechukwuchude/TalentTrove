# Auth + database foundation for a self-hosted backend

Status: approved design, pending spec review
Date: 2026-09-09

## Why

`packages/web` currently talks to TalentTrove's hosted server (`api.talenttrove.ai`)
for everything: sign-in, profile storage, tabs, job-postings search, and
judge. Searching against that server started coming back empty even for
maximally broad, unconditional queries — not a bug in this repo's request
code (traced and confirmed: the request sent is correct and minimal), but
something on the server or account side that this repo has no visibility or
control over. Rather than stay dependent on a server whose behavior we can't
diagnose or fix, we're replacing it entirely with our own backend.

Doing that is five largely-independent subsystems: auth, profile storage,
tabs, job postings + search, and judge. This spec covers only the first —
**auth and the database it needs to exist** — since every other piece needs
a signed-in user and a database to build on. The other four each get their
own spec/plan cycle later.

This supersedes the "Auth & session model" section of
`2026-09-08-web-app-migration-design.md`, which assumed the web app would
keep calling TalentTrove's hosted `/auth/send-code`/`/auth/verify-code`. That
assumption no longer holds for the auth piece; the rest of that spec (page
map, confirm-spend pattern, etc.) is unaffected until its corresponding
piece is replaced.

**Explicitly not in scope for this piece:** profile storage, tabs, job
postings/search, or judge. Replacing auth removes the TalentTrove `accessToken`
those routes currently forward to `api.talenttrove.ai` — so `/api/profile`,
`/api/tabs`, `/api/search`, and `/api/companies` will stop working the
moment this ships, until their own sub-projects replace them. That's an
accepted, temporary consequence of this being a personal/single-user
development setup rather than a live service with other users depending on
uptime — not something this piece works around.

## Database

Postgres, reached via a `DATABASE_URL` environment variable — no assumption
about where it's hosted (local Docker for dev, whatever gets provisioned for
production). Provisioning the instance itself is outside this project's
code.

Access via [Drizzle](https://orm.drizzle.team/): a typed, SQL-like query
builder with straightforward migrations (`drizzle-kit`), chosen over Prisma
(heavier, its own schema language and generated client) and over raw SQL
(no typed schema, fully manual migrations) as the middle ground for a small
app that doesn't need a lot of ceremony.

`packages/web/lib/db.ts` exports a single Drizzle client constructed from
`DATABASE_URL`, read the same way `SESSION_SECRET` is today (throw loudly if
unset — a missing database is a configuration error, not a "run in some
degraded mode" situation). Schema lives in `packages/web/db/schema.ts`;
migrations live in `packages/web/db/migrations/`, generated by
`drizzle-kit` and checked into the repo like any other source file.

### Schema

```
users
  id            uuid        primary key, default gen_random_uuid()
  email         text        unique, not null
  password_hash text        not null
  created_at    timestamptz not null, default now()
  failed_attempts   integer     not null, default 0
  locked_until      timestamptz null

sessions
  id          text        primary key   -- sha256(token), hex
  user_id     uuid        not null, references users(id) on delete cascade
  created_at  timestamptz not null, default now()
  expires_at  timestamptz not null

password_reset_tokens
  token_hash  text        primary key   -- sha256(token), hex
  user_id     uuid        not null, references users(id) on delete cascade
  expires_at  timestamptz not null
  consumed_at timestamptz null
```

`sessions.id` and `password_reset_tokens.token_hash` store a hash of the
actual token, never the raw value — the raw token exists only in the sealed
cookie (session) or the one-time reset email (reset token). A leaked
database dump alone can't be used to impersonate a session or redeem a
reset link.

`users.failed_attempts`/`locked_until` back the sign-in brute-force guard
(see "Error handling") without needing a separate table.

## Credential handling

- **Passwords**: hashed with Node's built-in `crypto.scrypt` (no new
  dependency, a well-regarded KDF), via a small `hashPassword`/
  `verifyPassword` pair in `packages/web/lib/passwords.ts`. Verification uses
  `crypto.timingSafeEqual` on the derived key, not `===`.
- **Session/reset tokens**: `crypto.randomBytes(32)`, base64url-encoded. The
  raw token round-trips through the sealed cookie (session) or the emailed
  link (reset); only `sha256(token)` (hex) is ever written to the database,
  and lookups hash the presented token before querying.
- **Minimum password length**: 8 characters. No composition rules (no
  forced mix of cases/digits/symbols) — length is the dimension that
  actually matters, and composition rules mostly push people toward
  predictable substitutions.

## Endpoints

Replacing today's `/api/auth/send-code`, `/api/auth/verify-code`, and
`/api/auth/handoff` (all TalentTrove-specific and no longer applicable — the
handoff route is dead code today anyway, kept only for interop with
TalentTrove's own hosted sign-in page, which nothing in this app's UI calls):

| Route | Body | Behavior |
|---|---|---|
| `POST /api/auth/sign-up` | `{email, password}` | 400 if the email is already registered, or the email/password fail validation. Otherwise: hash the password, create the user, create a session, set the cookie. Returns `{email}`. |
| `POST /api/auth/sign-in` | `{email, password}` | Look up the user by email; on any mismatch (no such email, or wrong password) return the same generic 400 `"that email or password is wrong"` — never reveal which one failed. On success: create a session, set the cookie, reset `failed_attempts`. Returns `{email}`. |
| `GET /api/auth/session` | — | Current session's `{email}`, or 401. Unchanged in shape from today. |
| `POST /api/auth/logout` | — | Delete the session row, clear the cookie. |
| `POST /api/auth/request-password-reset` | `{email}` | Always returns 200, regardless of whether the email exists (no account-enumeration via response or timing). Only actually creates a token and sends an email when the account exists. |
| `POST /api/auth/reset-password` | `{token, newPassword}` | 400 for an invalid/expired/already-consumed token or a weak password. On success: update `password_hash`, mark the token consumed, and delete every existing session for that user (a reset should also sign out anywhere a stolen password was being used). |

## Pages

`/sign-in` becomes a single page with a toggle between "Sign in" and
"Create account" (not separate routes) — same email+password fields either
way, submitting to `sign-in` or `sign-up` depending on the toggle state.

New: `/forgot-password` (email field, always shows the same "if an account
exists, we've sent a reset link" message) and `/reset-password?token=...`
(reads the token from the query string, takes a new password, redirects to
`/sign-in` on success).

## Session semantics

`requireSession(request)` reads the sealed cookie, hashes the token inside
it, and looks it up in `sessions` joined to `users`; if missing or past
`expires_at`, returns the same `{unauthorized: <401 response>}` shape it
does today. On success it returns `{userId, email}` — there is no more
access/refresh-token pair, so `withRenewedCookie`'s renewal dance goes away
entirely. A session is simply valid until it expires (fixed 30-day expiry
from creation, matching today's cookie lifetime) or its row is deleted
(logout, or a password reset).

**This changes what every other route destructures** (`auth.pass.accessToken`
→ `auth.userId`/`auth.email`). As part of this piece, `/api/profile`,
`/api/tabs`, `/api/search`, and `/api/companies` get updated to the new
`requireSession` shape and return a plain `501` ("not implemented yet") for
their actual data logic, rather than being left broken or failing to
compile. Real implementations arrive with each route's own sub-project.

## Error handling

- Sign-up: 400 duplicate email, 400 malformed email, 400 password under 8
  characters.
- Sign-in: generic 400 `"that email or password is wrong"` for both a
  nonexistent email and a wrong password.
- Sign-in brute-force guard: 5 consecutive failed attempts for an account
  locks it for 15 minutes (`locked_until`), tracked on the `users` row
  itself; a successful sign-in resets `failed_attempts` to 0. Locked-out
  sign-in attempts get a 429 with a plain "too many attempts, try again in
  N minutes" message.
- Password-reset request: always 200. A created reset token expires after
  30 minutes.
- Password-reset submit: 400 invalid/expired/consumed token, 400 weak new
  password.
- `SESSION_SECRET` (already required today, ≥32 characters) and
  `DATABASE_URL` are both read eagerly at startup/first use and throw loudly
  if missing — configuration errors, not degraded-mode situations.

## Testing

- **Pure logic, always run**: `hashPassword`/`verifyPassword` round-trip and
  timing-safe comparison, session/reset token generation and hashing,
  email/password validation. No database needed.
- **Route-level integration tests, gated on a real Postgres**: read
  `DATABASE_URL` (or a separate `TEST_DATABASE_URL` if set, to avoid ever
  running tests against a real dev database by accident); if neither is
  set, these tests are skipped (not failed), so the existing no-database
  test run stays green everywhere else. Covers sign-up, sign-in (including
  the generic-error and lockout behavior), session lookup/expiry, logout,
  and the full password-reset round-trip.
- A short section is added to `packages/web`'s README (or a new
  `packages/web/docs/testing.md` if none exists) on spinning up a local
  Postgres for running the gated tests.

## Migration/rollout note

This is not a live service with other users depending on uptime today — it
is developed and used by one person. Cutting over auth before profile/tabs/
search/judge are rebuilt is an accepted temporary state (those routes 501
until their own pieces land), not something staged behind a feature flag or
dual-run against both backends at once. The remaining four sub-projects are
expected to follow in fairly quick succession.

## Out of scope for this design

- Profile storage, tabs, job postings/search, and judge — each gets its own
  spec.
- OAuth/social sign-in (not present today either; not being added here).
- Any UI visual redesign beyond adding the sign-up toggle and two new pages
  in the existing Tailwind/shadcn style already established.
- Rate-limiting `request-password-reset` beyond what's implied by "always
  200, only sends if the account exists" (no per-IP throttling) — revisit if
  abuse is observed.
