# Apply: cover letters, application tracking, and a ready-to-apply queue

Status: approved design, pending spec review
Date: 2026-09-15

## Why

The original idea behind this whole line of work was "find roles, tailor a
CV, and apply for the applicant." Resume tailoring
(`2026-09-14-resume-tailoring-design.md`) built the first half. This spec
was meant to scope the second half — actually submitting the
application — but real submission turned out not to be legitimately
possible for any of this app's existing postings sources, and that finding
reshapes what this piece actually builds.

**What research found, checked against each platform's own primary API
documentation (not summaries or blog posts):**

- **Greenhouse**: its application-submission endpoint requires HTTP Basic
  Auth with an API key that belongs to the *hiring company*, generated by
  their own account admin. The docs explicitly warn the key is secret and
  must never be exposed to a public form post.
- **Lever**: same shape. Lever's own `postings-api` README states plainly
  — *"To use the POST API, you need an API key, which a Super Admin of
  your account can generate from your integrations settings page"* — the
  hiring company's account, not a third party's. The same document also
  states the API does not expose a posting's custom questions at all, and
  that Lever's own recommended best practice is to send candidates to
  *their* hosted application form rather than building a custom one.
- **Ashby**: its public API only documents job-listing retrieval.
  Application submission isn't part of the public surface; postings carry
  an `applyUrl` pointing at Ashby's own hosted apply page instead.
- **JSearch and Adzuna**: these are aggregators — a posting from either
  links out to an arbitrary third-party site (the employer's own careers
  page, another ATS entirely). There is no single API surface to target
  at all.

**Net effect: no existing source offers a legitimate way for this app to
submit an application on the applicant's behalf.** Every path to real
submission would require either obtaining private, employer-owned
credentials this app has no right to, or browser automation attempting to
drive an arbitrary site's real form — a much larger, more fragile,
ToS-riskier undertaking than anything else built in this app, which has
deliberately avoided headless-browser dependencies everywhere, including
in the resume-tailoring PDF work.

**So this piece does not submit anything.** It does the rest of the
preparation work — a cover letter alongside the resume tailoring already
produces, a way to track which prepared applications you've actually sent
yourself, and one place to see everything that's ready — and leaves the
actual act of applying to you, on the original site, exactly the way
Lever's own documentation recommends candidates be sent to a real hosted
form rather than a custom one.

**This app is expected to run autonomously** wherever autonomy is safe:
the cover letter is generated the same unattended way the résumé already
is. Marking something "applied," by contrast, is inherently something
only a person can attest to, so that part of this piece is manual by
nature, not a design choice to reconsider later.

## What already exists and must not be redesigned

- **`packages/web/lib/tailoring/run-tailoring.ts`** — the per-account,
  per-posting pipeline that already judges eligibility (`strong`/`fair`
  verdict), generates content via a forced-tool-call OpenRouter request,
  and renders/stores a PDF. This piece extends its existing tool call
  rather than adding a second one.
- **`packages/web/lib/tailoring/openrouter.ts`'s `tailorResumeContent`** —
  the forced-tool-call wrapper whose schema this piece extends by one
  field.
- **`packages/web/db/schema.ts`'s `tailoredResumes`** — the table this
  piece adds a column to; its `(user_id, posting_id)` unique index is
  already the "one tailored resume per posting per user" guarantee this
  piece's cover letter rides along with.
- **`packages/web/lib/postings-search.ts`/`tabs-db.ts`'s existing
  `LEFT JOIN`-and-flag pattern** (`has_tailored_resume`, `verdict`) — the
  precedent this piece's own queue query and the new `applications` join
  follow.

## Data model

**1. `tailoredResumes` gains one column**, populated in the same
insert that already writes `pdfBytes`/`model` — no separate nullable
state, no second failure mode:

```ts
coverLetter: text('cover_letter').notNull(),
```

**2. New `applications` table**, same shape as `judgments`/
`tailoredResumes`:

```ts
export const applications = pgTable(
  'applications',
  {
    id: uuid('id').primaryKey().defaultRandom(),
    userId: uuid('user_id')
      .notNull()
      .references(() => users.id, { onDelete: 'cascade' }),
    postingId: uuid('posting_id').notNull(), // not a FK — same reasoning as judgments/tailoredResumes
    appliedAt: timestamp('applied_at', { withTimezone: true }).notNull().defaultNow(),
  },
  (table) => [uniqueIndex('applications_user_id_posting_id_key').on(table.userId, table.postingId)],
);
```

The unique index is both the "already marked, don't duplicate" guard
(`onConflictDoNothing()`) and the join key the queue query filters on.

## Cover letter generation

`tailorResumeContent`'s tool schema (`packages/web/lib/tailoring/openrouter.ts`)
gains a required `coverLetter: string` property alongside the existing
`summary`/`skills`/`experience`/`education`, validated the same way the
other string fields already are (non-empty, else the whole call is
treated as `{error}` — same all-or-nothing contract the rest of the tool
call already has). `TailoredContent`'s type gains the matching field.
`run-tailoring.ts`'s insert into `tailoredResumes` gains
`coverLetter: content.coverLetter`. No new model call, no new env var, no
new cron job — this rides entirely inside the existing tailoring pipeline
and its existing per-posting failure isolation.

The system prompt instructing the model gains one sentence describing the
cover letter's purpose (brief, specific to the posting, professional tone)
— exact wording is an implementation-plan detail, not a spec-level
decision.

## Application tracking

- **`POST /api/applications/[postingId]`** — authenticated, scoped to the
  session's `userId`. Inserts an `applications` row with
  `onConflictDoNothing()` (idempotent — marking an already-marked posting
  applied again is a no-op, not an error). Returns `{applied: true}`.
- **`DELETE /api/applications/[postingId]`** — removes the row for that
  user/posting if present (idempotent whether or not one existed).
  Returns `{applied: false}`. Exists so a misclick isn't permanent, even
  though the `/apply` page's v1 UI doesn't surface an explicit undo
  button — reachable directly against the API, and cheap to wire a UI
  affordance to later if it turns out to matter.
- Neither route requires the posting or its tailored resume to exist —
  marking applied is a fact about the user's own action, not a
  correctness check against tailoring's state. (A posting with no
  `tailored_resumes` row simply never appeared in the queue to be marked
  from in the first place; the routes themselves stay simple.)

## The `/apply` page

- **`GET /api/applications/queue`** — authenticated, cursor-paginated
  (same shape as every other listing endpoint in this app). Backed by a
  new `packages/web/lib/applications-db.ts` exporting
  `getApplicationQueue(userId, limit, cursor)`: postings with a `strong`/
  `fair` `judgments` row for this user, a `tailoredResumes` row for this
  user (joined for `coverLetter` and the resume's existence), and **no**
  `applications` row for this user — the same `LEFT JOIN ... WHERE ...
  IS NULL` shape `postings-search.ts` already uses for its `unjudged`
  filter, just composed from a different pair of joins. This file is
  separate from `postings-search.ts` deliberately: the queue's filter
  set (verdict threshold + tailored + not-applied) is fixed and specific
  to this one view, not one more optional filter bolted onto general
  search.
- **`app/apply/page.tsx`** (thin server wrapper) +
  **`app/apply/apply-view.tsx`** (`'use client'`) — same split as
  `app/tabs/page.tsx`/`tabs-view.tsx`. A new
  `packages/web/lib/application-queries.ts` exports `useApplicationQueue()`
  (the list) and `useMarkApplied()`/`useUnmarkApplied()` (mutations),
  mirroring `tab-queries.ts`'s `useTabs()`/`useDeleteTab()` shape exactly
  — same TanStack Query cache-invalidation pattern, same loading/error
  rendering.
- Each queue entry renders: title/company/verdict badge (reusing
  `<PostingCard>`'s existing pieces where they fit), a link to
  `posting.url` (the original posting — where you actually apply,
  opening in a new tab), the existing "Download tailored resume" link,
  the cover letter shown inline with a "Copy" button, and a "Mark as
  applied" button. On success, the mutation removes that entry from the
  query cache immediately — no separate refetch needed, matching
  `useDeleteTab`'s existing optimistic-removal pattern.
- A posting that's been marked applied is not deleted or hidden from
  search/tabs elsewhere — it simply stops appearing in this one queue,
  since the queue's whole purpose is "what's left to act on."

## Error handling

Cover letter generation shares tailoring's existing all-or-nothing
per-call contract and per-posting/per-account failure isolation — nothing
new to add here, since it's inside the same tool call and the same insert
tailoring already wraps in try/catch. The two new routes are simple
authenticated CRUD with no external calls, so they have no distinct
failure modes beyond the standard 401 (not signed in) shape every other
route already follows.

## Testing

- **`db/schema.test.ts`**: new column on `tailored_resumes`, new
  `applications` table, its unique index — same migration-test pattern as
  every prior schema change.
- **`lib/tailoring/openrouter.test.ts`**: `tailorResumeContent`'s
  successful-response test asserts a `coverLetter` string is present; a
  new case asserts a response missing `coverLetter` is treated as
  `{error}`.
- **`lib/tailoring/run-tailoring.test.ts`**: the existing "tailors a
  posting successfully" case asserts the inserted `tailoredResumes` row
  carries the generated `coverLetter`.
- **`lib/applications-db.ts`** gated tests: a `strong`-verdict,
  tailored, unapplied posting appears in the queue; a `weak`-verdict one
  doesn't; an already-applied one doesn't; a tailored-but-unjudged one
  doesn't (shouldn't be reachable given tailoring's own gating, but worth
  asserting the query itself enforces it independently).
- **Route tests** for `POST`/`DELETE /api/applications/[postingId]` and
  `GET /api/applications/queue`: 401 when not signed in, idempotency of
  both mutations, and the queue's exclusion rules end-to-end through the
  route.
- **`apply-view.tsx`** component test: renders queue entries, "Mark as
  applied" removes the entry from the rendered list — mirroring
  `tabs-view.test.tsx`'s pattern for `useDeleteTab`.

## Migration/rollout note

Same framing as every prior piece: personal/single-user, no live traffic
to protect. `tailored_resumes.cover_letter` is added as `NOT NULL DEFAULT
''`, so any pre-existing row (from tailoring runs before this piece
shipped, e.g. in a local dev/test database) backfills to an empty string
rather than failing the migration; the default is then dropped in the
same migration so every row inserted from this point on must supply a
real value — the standard, reversible pattern for adding a `NOT NULL`
column to a table that might already have rows. `applications` is a new
table with nothing to migrate into it.

## Out of scope for this design

- **Actual submission of any kind**, anywhere — this is the core finding
  of this spec; see "Why" above. Not deferred pending future research;
  deferred because it isn't legitimately possible against any source this
  app ingests from today.
- Browser automation as a path to submission — flagged during
  brainstorming, explicitly not chosen.
- Mark-as-applied affordance on ordinary posting cards in search/tabs —
  v1 only surfaces it on the dedicated `/apply` queue page.
- An "undo" UI button for unmarking — the `DELETE` route exists and is
  cheap to wire a button to later; not built now.
- Custom-question answering of any kind — moot once no source's API
  accepts a submission at all.
